# OUTFIT-08 — wardrobe readiness и честные gaps

Статус: **PASS — продуктовый и UX-контракт готов; HOLD — runtime для диапазонов и gaps не реализован и не проверен**  
Область: только личный гардероб на устройстве; demo — отдельный явно маркированный режим  
Вне scope: Auth, Supabase, VK ID, платежи, магазины, ссылки на товары и любые внешние retail-рекомендации

## Решение

Readiness отвечает не на вопрос «достаточно ли у человека вещей вообще», а на более узкий вопрос: **можно ли сейчас составить хотя бы один честный образ для выбранного сценария только из подтверждённых личных вещей**.

Диапазоны `1–7`, `8–15` и `16+` — это маршрутизация глубины помощи, а не публичный балл качества гардероба и не обещание результата. Количество не заменяет проверку состава: 16 вещей одного типа могут не дать полного образа, а три подтверждённые вещи могут дать его.

Система:

- считает только записи с `source: "personal"`, стабильным `id` и доступным статусом;
- никогда не дополняет личный результат demo-вещами, вымышленными вещами или товарами;
- не объявляет неизвестное отсутствующим: `unknown` ведёт к просьбе уточнить карточку, а не к gap;
- показывает максимум один ближайший полезный шаг и не делает покупку обязательным продолжением;
- хранит и обрабатывает readiness локально в существующей personal-области; сетевые вызовы для расчёта не нужны;
- не публикует score, процент «готовности», рейтинг гардероба или сравнение с другими людьми.

## Термины и вход

`personal item` — вещь текущего локального владельца с `source: "personal"`. Demo-запись, временный магазинный якорь, удалённая/архивная вещь и запись другого owner scope не являются личной доступной вещью.

`confirmed category` — категория, которую пользователь выбрал или подтвердил. Результат распознавания без подтверждения и значение `unknown` не считаются подтверждённой категорией.

`scenario` — явный запрос пользователя: повод/дресс-код и, если заданы, погода и ограничения. Если сценарий не задан, readiness может показать инвентарный обзор, но не утверждает, что гардероб готов «на все случаи».

`functional gap` — минимальная роль, без которой нельзя построить образ в данном сценарии из подтверждённых личных вещей. Это не товар и не диагноз гардероба.

Минимальный вход расчёта:

```text
ownerScope
mode = personal
wardrobe[]: id, source, availability/status, confirmed, category
scenario?: occasion, dressCode, weather, explicit constraints
```

Дополнительные свойства — сезонность, тепло, waterproof, посадка и другие — используются только когда они явно заданы или подтверждены. Отсутствующее свойство остаётся `unknown`.

## Два независимых результата

Расчёт возвращает два значения, которые UI не должен склеивать:

1. `inventory_band`: `one_to_seven | eight_to_fifteen | sixteen_plus`. Это только размер подтверждённого личного набора.
2. `scenario_readiness`: `ready | needs_confirmation | gap | no_scenario | unavailable`.

Приоритет fail-closed:

1. Невалидный mode/scope или смешение personal/demo → `unavailable`, без результата и gaps.
2. Есть неизвестные данные, которые могут изменить вывод → `needs_confirmation`.
3. Подтверждённо нет обязательной роли → `gap`.
4. Есть хотя бы один валидный личный кандидат для сценария → `ready`.
5. Сценарий не задан → `no_scenario`; разрешён только нейтральный обзор.

`item_count` допустим как приватный факт интерфейса («Добавлено 6 вещей»), но не преобразуется в score. Телеметрия, если она появится, принимает только band и reason code без названий, фото, item IDs, owner ID и содержимого гардероба.

## Поведение по диапазонам

| Личных подтверждённых вещей | Что честно показать | Что предложить | Что запрещено |
|---|---|---|---|
| **1–7** | Ценность одной вещи: выбрать якорь и проверить, есть ли к нему полный личный комплект. Если полного комплекта нет — назвать одну подтверждённо отсутствующую роль. | «Добавить вещь из гардероба», «Уточнить категорию», «Выбрать другой сценарий». Demo доступен только отдельной кнопкой «Посмотреть пример» с постоянной маркировкой. | «Гардероб недостаточный», требование набрать N вещей, автоматическая подстановка demo, призыв купить gap. |
| **8–15** | Несколько личных сочетаний, если они реально существуют; показать покрытие выбранного сценария и одну ближайшую функциональную развилку. | Собрать сейчас; сменить якорь/сценарий; отметить уже имеющуюся, но не добавленную вещь через обычный local intake. | Обещать капсулу только по количеству, перечислять «обязательные покупки», создавать дефицит из неизвестных свойств. |
| **16+** | Не «полная готовность», а больше выбор: фильтры по сценарию, повторяемости и явно заданным ограничениям. Gap показывается только для текущего сценария. | Сузить запрос, использовать то, что уже есть, скрыть/архивировать недоступное, уточнить спорные карточки. | Публичный score, оценка «слишком много/мало», сравнение с нормой, upsell за полноту гардероба. |

Число вещей влияет только на подачу. Во всех трёх диапазонах кнопка «Собрать» активна при `scenario_readiness = ready`, а не при достижении порога 8 или 16.

## Как определять readiness

### 1. Отфильтровать допустимый набор

В расчёт входят только personal-вещи текущего scope с непустым уникальным `id`, доступным статусом и подтверждённой карточкой. Смешанный scope или присутствие demo в personal payload — ошибка границы, а не повод тихо отфильтровать данные и продолжить.

Дубликаты ID, повреждённые записи и неизвестная версия схемы дают `unavailable` с безопасным действием «Обновить данные / попробовать снова». Они не уменьшают count молча.

### 2. Построить роли выбранного сценария

Базовые пути полного образа:

- `top + bottom + shoes`;
- `one_piece/dress + shoes`.

Верхний слой, дополнительный слой или погодное свойство становятся обязательными только из явного сценария/ограничения. Аксессуары по умолчанию необязательны и не могут блокировать readiness.

Эти пути — стартовый продуктовый контракт, не универсальное правило одежды. Пользователь может изменить сценарий или явные ограничения; интерфейс не делает гендерных, культурных, возрастных или телесных предположений.

### 3. Отделить `unknown` от подтверждённого отсутствия

Если нужная роль может находиться среди вещей с неподтверждённой категорией, результат — `needs_confirmation`, например: «У двух вещей не указана категория. Уточните одну, чтобы проверить образ». Формулировка «не хватает обуви» допустима только когда все релевантные доступные personal-карточки проверены и обувь действительно отсутствует.

Для погоды действует тот же принцип:

- `waterproof: false` у всей релевантной обуви + дождь как hard constraint → подтверждённый functional gap;
- `waterproof: unknown` → `needs_confirmation`, не «нет непромокаемой обуви»;
- погода не задана → погодные gaps не выводятся.

### 4. Проверить реального кандидата

`ready` означает, что генератор вернул хотя бы один непустой кандидат, где каждая вещь:

- имеет `source: "personal"`;
- существует по ID в переданном personal wardrobe;
- доступна и подтверждена;
- удовлетворяет hard constraints сценария.

Количество, визуальная совместимость или внутренний score отдельно не дают право поставить `ready`. Ошибка генерации не заменяется demo: показывается нейтральное «Не удалось проверить образ. Попробовать снова».

## Модель gaps без давления купить

Разрешённые reason codes:

```text
missing_top
missing_bottom
missing_one_piece_or_separates
missing_shoes
missing_required_layer
missing_confirmed_weather_property
category_confirmation_needed
property_confirmation_needed
no_candidate_for_constraints
data_unavailable
```

Gap содержит только:

```text
reason_code
scenario_label
missing_role                 # только если отсутствие подтверждено
evidence: confirmed counts  # агрегаты, без фото и публичного score
next_actions[]               # local-first, некоммерческие
```

Порядок next actions:

1. Использовать/выбрать подходящую вещь, которая уже есть в личном гардеробе.
2. Уточнить неизвестную категорию или свойство.
3. Добавить уже принадлежащую пользователю вещь в локальный гардероб.
4. Ослабить или изменить сценарий/ограничение по явному выбору пользователя.
5. Закрыть карточку и продолжить без действия.

Фразы «купить», «докупить», «вам обязательно нужно», цены, бренды, товарные ссылки и retail CTA в readiness/gaps запрещены. Даже подтверждённый gap формулируется так: «Для этого сценария среди добавленных вещей не найдена обувь» и сопровождается действиями «Добавить свою обувь» / «Изменить сценарий» / «Закрыть».

Одновременно показывается один самый близкий блокирующий gap. Остальные можно раскрыть по запросу как «Что ещё проверить», без тревожной красной индикации. Gap относится к сценарию, а не к человеку: «для дождливой прогулки», не «ваш гардероб неполный».

## Copy contract

### 1–7, кандидат есть

- Заголовок: «Можно собрать из ваших вещей».
- Текст: «Нашёлся личный комплект для выбранного сценария. Демо-вещи не используются».
- Primary CTA: «Собрать из моих вещей».
- Secondary CTA: «Добавить ещё свою вещь».

### 1–7, подтверждённый gap

- Заголовок: «Пока не складывается полный комплект».
- Текст: «Для этого сценария среди добавленных вещей не найдена обувь».
- CTA: «Добавить свою обувь», «Изменить сценарий», «Закрыть».

### Есть unknown

- Заголовок: «Нужно уточнить одну вещь».
- Текст: «У части вещей не указана категория, поэтому мы пока не можем честно сказать, чего не хватает».
- CTA: «Уточнить карточки», «Не сейчас».

### 8–15 или 16+, кандидат есть

- Заголовок: «Есть варианты для этого сценария».
- Текст: «Покажем только сочетания из вашего личного гардероба».
- CTA: «Показать варианты»; для 16+ допустимо «Сузить выбор».

### Ошибка или повреждённые данные

- Заголовок: «Не удалось проверить готовность».
- Текст: «Мы не будем подставлять пример вместо личного результата».
- CTA: «Попробовать снова».

Нельзя использовать: «готовность 72%», «гардероб слабый/идеальный», «у вас мало вещей», «must-have», «закройте пробел покупкой», «всем нужна базовая белая рубашка».

## Demo/personal separation

- Demo никогда не участвует в `item_count`, band, readiness, gap evidence или personal candidate.
- Переход в demo — только явное действие пользователя; экран, карточки и результат имеют видимую метку «Демо-пример».
- Возврат из demo повторно считает readiness только по personal wardrobe.
- Demo-результат нельзя сохранить как personal, использовать как evidence наличия роли или представить фразой «из ваших вещей».
- Любой mixed personal/demo candidate отклоняется как `unverified_personal_result`; интерфейс показывает ошибку без fallback.

## Privacy и хранение

- Расчёт выполняется локально поверх существующего repository boundary; документ не вводит новый storage key или сетевой адаптер.
- В readiness достаточно структурированных карточек. Фото, object URL, data URL, EXIF, имена файлов и исходные изображения в расчёт, gaps и телеметрию не передаются.
- UI не раскрывает readiness/gaps публично и не создаёт shareable score.
- При `meta.persisted !== true` интерфейс сообщает «Не сохранено на устройстве» и не подтверждает долговечное обновление readiness после добавления вещи.
- Удаление/архивация вещи и смена scenario инвалидируют прежний результат; следующий показ пересчитывается из актуального локального набора.

## Acceptance criteria

1. Для наборов 1, 7, 8, 15, 16 и 30 personal-вещей band детерминирован и не используется как gate сборки.
2. Набор из `top + bottom + shoes` может быть `ready` даже при 3 вещах; 16 `top` дают подтверждённый `gap`, а не `ready`.
3. Путь `dress/one_piece + shoes` не требует отдельно top/bottom.
4. Unknown-категория или неизвестное hard-свойство, способные закрыть роль, дают `needs_confirmation`, а не gap.
5. Demo, temporary retail anchor, archived/deleted и cross-owner записи не считаются personal; mixed mode/scope fail closed.
6. Каждый personal result содержит только IDs из актуального personal wardrobe; пустой/смешанный результат отклоняется.
7. Ошибка генерации не открывает demo и не создаёт вымышленный результат.
8. UI показывает не больше одного первичного gap, привязывает его к сценарию и всегда даёт «Не сейчас/Закрыть».
9. Ни в одном band нет price, brand, purchase CTA, товарной ссылки, публичного score или нормативной оценки количества вещей.
10. При отсутствии scenario система не заявляет универсальную готовность и не создаёт погодные/occasion gaps.
11. Unit fixtures покрывают обе базовые формулы, hard weather unknown/false, duplicate ID, malformed data, mixed demo/personal и boundary 7/8/15/16.
12. Локальная проверка подтверждает отсутствие сетевых запросов и photo payload в readiness flow.

## Evidence в текущем tree

- `src/honestReadiness.js`: считает только `source: "personal"`; personal result проверяет source и принадлежность ID; ошибка не подменяется demo.
- `src/honestReadiness.test.js`: есть проверки personal-only count, явного demo, отклонения mixed result и отсутствия demo fallback.
- `docs/RELEASE-03-INTEGRATION.md`: фиксирует local-only integration contract и обязанность category/constraint check не считать demo.
- `docs/local-storage-boundary.md`: фиксирует локальный repository boundary, `meta.persisted` и запрет неявной передачи фото будущему server adapter.
- `src/capsuleEngine.test.js`: содержит релевантные примеры honest hold для hard weather, unknown-признаков и малого гардероба; это evidence принципа, но не доказательство интеграции OUTFIT-08.

Текущее evidence подтверждает базовую personal/demo защиту, но **не подтверждает** band-specific UX, unknown-vs-gap resolver, scenario-scoped gaps или acceptance matrix этого документа.

## Зависимости и handoff

Для снятия runtime HOLD нужны:

1. Product/domain owner: стабильная taxonomy ролей и явное представление `confirmed`/`unknown` для категории и hard-свойств.
2. Outfit engine owner: функция, возвращающая candidate и стабильные reason codes без публичного score; проверка актуального personal membership.
3. UI owner: band-specific copy, один gap, dismiss/«Не сейчас», явная demo-маркировка и отсутствие purchase CTA.
4. Local persistence owner: актуальный personal snapshot и честная обработка `meta.persisted !== true`; без нового cloud boundary.
5. QA: boundary fixtures `7/8/15/16`, category distributions, unknown/false weather, mixed mode/scope, storage failure и проверка отсутствия network/photo leakage.

Интеграционный gate: **HOLD**, пока пункты 1–5 не реализованы и не подтверждены тестами. После этого PASS требует unit + UI integration evidence; Auth/Supabase/VK ID/payments/external retail не являются зависимостями OUTFIT-08 и не должны подключаться для снятия этого HOLD.
