# OUTFIT-01 — продуктовый CJM персонального образа

**Статус:** продуктовый CJM и UX-контракт — **PASS**; production implementation / release — **HOLD**  
**Дата:** 21 августа 2026  
**Scope:** только личный гардероб: путь от цели или якорной вещи до трёх носибельных вариантов, объяснения, замены и явного feedback. Auth, Supabase, VK ID, payments и внешний retail вне scope.

## 1. Решение

Основной продуктовый сценарий — короткая управляемая сессия «собрать образ сейчас». Пользователь начинает с цели либо с конкретной личной вещи, при необходимости уточняет минимум контекста и получает до трёх **технически полных и действительно различающихся** вариантов. Каждый вариант объясняется обычным языком без публичного числового score. Из результата можно заменить одну вещь, изменить условия, сохранить/отметить подходящий вариант или дать обратную связь.

Обещание интерфейса: **«Соберём до трёх вариантов из ваших вещей и честно скажем, если данных или вещей не хватает»**. Число три — максимум, а не обязательная квота: один честный полный вариант лучше трёх, созданных за счёт неподтверждённых предположений или неполных комплектов.

**PASS:** продуктовый путь, состояния, тексты решений и acceptance criteria определены и совместимы с существующими локальными wardrobe, candidate, explanation и learning-контрактами.

**HOLD:** документ не доказывает готовность production-сценария. Нужны интеграция единого flow, snapshot-сохранение результата, закрытый feedback → ranking loop, UI и browser/e2e-проверки. Production photo recognition не является зависимостью и остаётся отдельным HOLD.

## 2. Неподвижные границы

1. **Только personal wardrobe.** В персональный запрос допускаются только вещи с подтверждённым `source=personal`. Demo — отдельный маркированный preview; его вещи нельзя смешивать с personal, сохранять как личный образ или использовать для обучения личного профиля.
2. **Local-first и private-by-default.** Генерация, черновик, feedback и сохранение в этом контуре проектируются локальными. Нельзя заявлять синхронизацию или облачное сохранение. Успех сохранения показывается только после положительного persistence receipt/read-back.
3. **Без скрытого распознавания.** Фото не требуется для сценария. Используются подтверждённые редактируемые признаки карточек; неизвестное остаётся `unknown`. Никакой отправки фото, EXIF, имени файла или item payload во внешнюю сеть.
4. **Без чувствительных inference.** Не выводить пол, возраст, тело, размер/пропорции, цветотип, этничность, привлекательность или демографию. Посадка, комфорт и предпочтения — только явные пользовательские данные.
5. **Unknown-safe.** Неизвестный признак не считается совпадением и не превращается в уверенную рекомендацию. Он вызывает нейтральный текст, уточнение, понижение качественной уверенности или исключение по hard gate.
6. **Hard gate раньше ranking.** Полный базовый образ: `top + bottom + shoes` либо `dress/one_piece + shoes`; обязательная по подтверждённому контексту верхняя одежда тоже входит в gate. Score не компенсирует отсутствие категории, anchor или доступности вещи.
7. **Нет публичных score.** В UI разрешены только качественные причины, trade-off и `high|medium|low` confidence при наличии трассируемого основания. Веса, баллы и внутренний ranking не показываются и не используются как псевдообъективная оценка пользователя.
8. **Feedback явный, обратимый и минимальный.** Один клик не становится вечным запретом. Пользователь видит, что запомнено, и может Undo/Reset/Export/Delete. Отрицательная реакция описывает образ, а не человека.
9. **Без retail/paywall.** Если категории не хватает, выходы — добавить свою вещь, изменить цель/условия, продолжить с честным ограничением или выйти. Товарные предложения, платежи и внешние магазины отсутствуют.

## 3. Определение успешного результата

`OutfitSessionV1` — будущая продуктовая сущность, не заявление о готовом runtime:

| Поле | Назначение |
|---|---|
| `session_id`, `schema_version`, `created_at` | воспроизводимость и миграции |
| `source_scope=personal` | fail-closed запрет demo/personal mixing |
| `entry_mode` | `goal` или `anchor` |
| `goal` | occasion/задача пользователя; может быть `unspecified` до уточнения |
| `anchor_item_id` | только подтверждённая доступная personal-вещь либо `null` |
| `context_snapshot` | погода/температура, indoor/outdoor, активность, dress code, комфорт — только известные поля |
| `wardrobe_revision` | версия входного набора вещей |
| `variants[]` | 1–3 полных варианта, item ids/snapshots, качественные причины, unknowns и trade-offs |
| `engine_versions` | версии генератора, ruleset, explanation и preference snapshot |
| `status` | `draft`, `needs_input`, `ready`, `limited`, `saved`, `discarded` |
| `feedback_refs[]` | ссылки на явные события и их undo, без свободного текста в аналитике |

Носибельный вариант в рамках контракта:

- состоит только из доступных personal-вещей текущего запроса;
- проходит техническую комплектность и все известные hard constraints;
- включает anchor, если пользователь начал с него;
- не опирается на неизвестное как на подтверждённый факт;
- объясняет, для какой цели подходит, почему вещи работают вместе и где есть неопределённость;
- допускает действие «заменить вещь» без потери остальных подтверждённых условий.

Три результата должны отличаться заметным пользовательским решением: ключевой вещью, силуэтом, уровнем формальности или цветовой ролью. Простая перестановка аксессуара не считается самостоятельным вариантом. Исключение — anchor может повторяться во всех трёх.

## 4. End-to-end CJM

| Этап | Действие пользователя | Ответ продукта | Успешный выход |
|---|---|---|---|
| 1. Вход | Нажимает «Собрать образ» | Два равноправных старта: «Для чего образ?» и «Начать с вещи» | Выбран `goal` или personal anchor |
| 2. Контекст | Выбирает ситуацию/цель и, если нужно, уточняет условия | Задаются только вопросы, влияющие на hard gate или заметный выбор; у каждого есть «Пропустить» и объяснение зачем | Валидный минимальный brief либо явные unknowns |
| 3. Проверка | Подтверждает anchor, доступность и исключения | Проверяются personal source, категории, статус вещей и обязательные условия | `ready_to_generate` или понятный gap |
| 4. Генерация | Нажимает «Показать варианты» | Детерминированно строятся полные кандидаты, затем diversity; система не добивает количество неполными образами | 1–3 валидных варианта либо `limited` |
| 5. Объяснение | Просматривает карточку варианта | Видит короткое «почему», контекст, trade-off и неизвестные данные; может раскрыть детали | Выбор понятен без баллов и экспертного жаргона |
| 6. Замена | Нажимает на конкретную вещь → «Заменить» | Фиксируются цель, anchor и остальные вещи; показываются допустимые личные альтернативы и причина отсутствия, если их нет | Обновлён только выбранный вариант |
| 7. Решение | Выбирает «Надела бы», сохраняет либо отмечает «Не моё» | Положительный выбор не равен факту носки; сохранение и feedback — отдельные действия | Явный outcome без скрытого обучения |
| 8. Feedback | Для отрицательной реакции выбирает короткую причину | Разрешены причины про цвет, формальность, посадку, обувь, температуру или «не мой стиль»; есть «Не запоминать» | Событие записано с consent/receipt либо применено только к сессии |
| 9. Возврат | Открывает сохранённый образ | Показывается snapshot и статус доступности вещей; пересборка создаёт новую версию, а не молча меняет старую | Результат воспроизводим и объясним |

### 4.1 Старт от цели

Минимум — одна цель: например, работа, прогулка, встреча, событие или «на каждый день». Это продуктовая taxonomy, а не свободная генерация фактов. Дополнительные поля появляются только по необходимости:

- indoor/outdoor и длительность — если влияют на тепло/слои;
- ручная погода/диапазон — опционально; без геолокации сценарий остаётся рабочим;
- dress code и желаемая формальность;
- активность и явные ограничения комфорта;
- «не использовать сегодня» для временно недоступных вещей.

Если цель слишком общая, продукт задаёт один наиболее полезный вопрос. Если пользователь пропускает, выдача возможна только с нейтральной формулировкой и отмеченным unknown; нельзя утверждать соответствие неизвестному dress code или погоде.

### 4.2 Старт от якорной вещи

Пользователь выбирает вещь из personal wardrobe. Перед генерацией система подтверждает: вещь доступна, её категория известна и она может быть частью полного комплекта. Далее предлагается выбрать цель или «просто собрать варианты»; во втором случае соответствие occasion не заявляется.

Anchor обязан присутствовать во всех вариантах и после замены других элементов. Сам anchor заменяется только отдельным подтверждённым действием «Сменить якорь», после которого это новая генерация. Если anchor удалён, недоступен или имеет неизвестную категорию, состояние — `needs_input`, а не тихий fallback на другую вещь.

## 5. Экран результата: до трёх вариантов

Порядок карточки:

1. Название по назначению, не оценка личности: «Спокойный вариант для офиса».
2. Состав с явными названиями personal-вещей.
3. Короткое объяснение из 1–3 подтверждённых причин: цель/формальность, сочетание известных признаков, комфорт/погода.
4. Блок «Стоит учесть», если есть trade-off или unknown.
5. Действия: `Надела бы`, `Заменить вещь`, `Не моё`, `Сохранить`.

Пример unknown-safe copy: «Для этой вещи не указана теплота, поэтому мы не учитывали её как защиту от холода». Запрещено: «Вам идеально подходит», «стройнит», «омолаживает», «ваш цветотип» и любые объяснения, для которых нет подтверждённого fact/evidence.

Если найдено меньше трёх:

- 2 варианта: «Нашли два достаточно разных полных варианта»;
- 1 вариант: «Нашли один полный вариант без догадок»;
- 0 вариантов: не показывать пустые карточки; назвать стабильные gap-reasons и следующие действия.

## 6. Замена без полной потери контекста

Замена — локальная операция над выбранным вариантом:

1. Пользователь выбирает элемент, например обувь.
2. Система исключает текущую вещь для этой операции и оставляет цель, anchor, hard constraints и остальные элементы зафиксированными.
3. Альтернативы ищутся только в personal wardrobe и сначала проходят hard gate.
4. Показывается до трёх замен с качественным изменением: «менее формально», «теплее», «нейтральнее по цвету». Публичного score нет.
5. Применение создаёт новую revision варианта; отмена возвращает исходный вариант без feedback.

Если замены нет, интерфейс называет причину: `no_personal_alternative`, `missing_required_category`, `anchor_locked`, `constraint_conflict` или `unknown_item_data`. Доступны: вернуть исходную вещь, изменить одно ограничение, добавить/уточнить свою вещь или оставить текущий вариант. Внешний поиск не предлагается.

Замена становится learning feedback только после отдельного выбора «Запомнить эту замену» либо в явно согласованном feedback-контуре. Техническое действие в UI само по себе не доказывает устойчивое предпочтение.

## 7. Feedback и обучение

Три основные реакции соответствуют существующему learning contract:

| Действие | Смысл в текущей сессии | Долгосрочная запись |
|---|---|---|
| `would_wear` | повысить выбранный вариант/закончить выбор | только при явном consent; это «выбрано», не «надето» |
| `not_for_me` | убрать вариант из текущей выдачи | причина обязательна; слабый обратимый сигнал |
| `replace_item` | заменить указанную вещь | id вещи и причина обязательны; не permanent по умолчанию |

Разрешённые причины: `colors`, `too_dressy`, `fit`, `shoes`, `too_hot`, `too_cold`, `not_my_style`. Свободный текст можно хранить локально только при отдельном обосновании, но он не входит в ranking/analytics V1. Выбор `permanent=true` допустим лишь как отдельное явное «Больше не предлагать эту вещь», а не как следствие одного отрицательного клика.

После записи показывается конкретный receipt: «Учтём в следующих вариантах · Отменить». При отказе от consent реакция действует лишь в текущей сессии. Панель «Что стилист запомнил» предоставляет Undo/Reset/Export/Delete и не заявляет production/cloud learning, пока соответствующих evidence нет.

## 8. Состояния и нетупиковые ветки

`entry → brief → inventory_check → generating → results → saved|discarded`

Ветки:

- `brief → needs_input → brief`: неизвестно обязательное условие;
- `inventory_check → limited`: нет полного комплекта;
- `limited → edit_context | add_or_edit_personal_item | retry | exit`;
- `results → replace → results`: пересчитан один вариант;
- `results → feedback → results | saved`: явная обратная связь;
- `saved → regenerate_as_new`: новая revision без мутации snapshot.

Ошибки storage не маскируются: при `meta.persisted=false` остается рабочий in-memory результат и текст «Не сохранено на устройстве» с Retry/Export, но не success-toast. Повтор генерации при одинаковом snapshot и версиях должен быть детерминированным; изменение preference/profile revision объясняет новый порядок.

## 9. Demo и personal separation

- Demo доступен только как onboarding-preview с постоянной меткой «Пример, не ваш гардероб».
- Из demo нет действий `Сохранить в мои образы`, `Надела бы` с learning-записью или выбора demo-anchor для personal flow.
- CTA demo — «Добавить мою вещь»/«Открыть мой гардероб»; после перехода входной набор полностью заменяется personal-набором.
- Любой смешанный input должен завершаться fail-closed `mixed_source_scope`, а не фильтроваться молча: пользователь должен понимать, почему результат не построен.
- Аналитика demo и personal использует разные enum контексты; opaque session id не связывается с фото или содержимым гардероба.

## 10. Минимальная аналитика

Допустимы только allowlist-события с enum/bucket-полями: `outfit_started(entry_mode)`, `outfit_brief_ready(context_completeness_bucket)`, `outfit_generated(outcome, variant_count_bucket)`, `outfit_gap_shown(reason_code)`, `outfit_replace_requested(category_code)`, `outfit_feedback(action, reason_code)`, `outfit_saved(persisted)`.

Запрещены в телеметрии: item ids/names/payload, фото и производные, EXIF/имя файла, город/GPS, свободный текст, внутренние score/weights, чувствительные признаки и содержимое remembered profile. Local-only продукт должен оставаться работоспособным при полном отказе от аналитики.

## 11. Acceptance criteria

### Product / UX — PASS, если

- [ ] На входе равноправно доступны цель и personal anchor; фото, аккаунт, погода и покупка не обязательны.
- [ ] Personal request содержит только `source=personal`; mixed/demo input отклоняется fail-closed и объяснимо.
- [ ] Anchor присутствует во всех вариантах и не заменяется скрыто.
- [ ] Каждый показанный вариант технически полный и проходит известные hard constraints.
- [ ] Выдаётся от 1 до 3 вариантов; система не создаёт дубликаты или неполные комплекты ради числа три.
- [ ] Варианты заметно различаются, при этом anchor может повторяться.
- [ ] Объяснение строится только по подтверждённым allowlist-фактам; unknown не превращается в утверждение.
- [ ] UI не показывает числовой score, веса, рейтинг внешности или псевдообъективную «идеальность».
- [ ] Замена сохраняет контекст и остальные вещи, а отсутствие альтернативы имеет стабильную причину и выход.
- [ ] `not_for_me` и `replace_item` требуют причины; feedback можно не запоминать и можно отменить.
- [ ] Один feedback не создаёт permanent ban; пользователь может просмотреть/Undo/Reset/Export/Delete запомненное.
- [ ] Ошибка local persistence не показывается как сохранение; старый snapshot не мутируется молча.

### Обязательные edge cases

- [ ] 0 вещей: спокойный empty state и ручной путь добавления personal-вещи.
- [ ] 1 anchor: перечислены недостающие категории; готовый образ не заявляется.
- [ ] Много вещей, но нет обуви/базы: `limited` с точной причиной, независимо от item count.
- [ ] Неизвестная категория anchor: запрос уточнения, без автозамены и догадки.
- [ ] Неизвестная погода: нет утверждений о тепловой пригодности; сценарий можно продолжить без погоды.
- [ ] Удалённая/недоступная вещь в сохранённом snapshot: старый образ виден как snapshot, новая генерация её не использует.
- [ ] После replacement нет валидного комплекта: исходный вариант сохраняется до подтверждения замены.
- [ ] Storage quota/unavailable: in-memory сессия не теряется, показаны Retry/Export и честный статус.

### Release — HOLD, пока не выполнено

- [ ] Есть единый интегрированный `OutfitSessionV1`/controller с source guards, revisions и snapshot repository.
- [ ] Закрыт feedback → следующий ranking loop с consent, ETag/idempotency, undo и decay.
- [ ] Explanation UI использует allowlist renderer и не протекает внутренними score/evidence.
- [ ] Unit/integration/browser tests покрывают оба entry mode, 0/1/2/3 результата, replacement и storage failures.
- [ ] Доказаны network-before-consent=0 и отсутствие private payload в telemetry.
- [ ] Mobile и keyboard/screen-reader flow проверены на реальном UI.

## 12. Риски и gates

| Риск | Приоритет | Gate / мера |
|---|---:|---|
| Demo смешивается с personal или обучает профиль | P0 privacy | `source_scope` guard, negative tests, разные CTA/events |
| Неполный комплект показан как носибельный | P0 trust | hard gate до ranking; stable missing reasons |
| Unknown превращается в уверенный совет | P0 trust | allowlist facts, unknown bucket, forbidden-claim scan |
| Внешний score выглядит как оценка человека | P0 harm | числовые score/weights только внутренние; UI contract tests |
| Feedback записывается без consent или навсегда | P0 privacy | consent receipt, reversible weak signal, permanent only explicit |
| Сохранение заявлено при local storage failure | P0 data | `meta.persisted` + read-back; retry/export state |
| Три почти одинаковых варианта создают ложный выбор | P1 UX | post-rank diversity и overlap tests, кроме anchor |
| Замена пересобирает всё и нарушает ожидание | P1 UX | locked context/items; variant revision and undo |
| Старая карточка незаметно меняется после wardrobe edit | P1 data | immutable snapshot; regenerate-as-new |
| Контекст разрастается в анкету | P1 activation | progressive questions; один вопрос за раз; skip |
| Техническое действие ошибочно считается предпочтением | P1 learning | отдельное «Запомнить» и session-only default без consent |

## 13. Evidence и зависимости

### Существующая evidence в репозитории

- `src/stylistCandidateEngine.js`: anchor check, технически полные кандидаты, hard constraints, stable no-candidate reasons, deterministic ranking/diversity и qualitative `rankingReasons`.
- `src/outfitEngine.js`: flow-адаптер и функции missing categories для общего и anchor-сценария.
- `src/stylistExplanation.js` + `docs/stylist-explanation.md`: allowlist renderer, отбрасывание неподтверждённых фактов, unknown-code fallback, действия замены без раскрытия score.
- `src/stylistLearning.js` + `docs/stylist-learning-contract.md`: три feedback action, обязательные причины, consent/owner/idempotency/ETag, undo, decay и remembered view.
- `docs/local-storage-boundary.md`: versioned local repository, persistence metadata, export/delete/reset и запрет считать неуспешную запись сохранением.
- `docs/MVP-MAGIC-05-real-stylist-contract.md`: целевой hard gate → ranking → diversity → explanation → feedback loop и явно зафиксированные интеграционные разрывы.

Эта evidence подтверждает совместимость направления, но **не** является доказательством собранного end-to-end OUTFIT-01 в production UI.

### Зависимости реализации

1. Единый session/controller поверх wardrobe revision, candidate engine, explanation и learning adapter.
2. Personal-source guard и отдельный demo adapter без смешивания данных и feedback.
3. Snapshot repository для сохранённых вариантов с persistence receipt и export/delete.
4. Контракт локальной замены с locked anchor/context и стабильными no-alternative reasons.
5. Закрытие feedback → ranking integration с явным consent и preference version.
6. Accessible mobile UI и regression/e2e-набор для privacy, unknown-safe, replacement и storage failure.

Не являются зависимостями OUTFIT-01: auth, Supabase, VK ID, payments, внешний retail, cloud sync и production photo recognition.
