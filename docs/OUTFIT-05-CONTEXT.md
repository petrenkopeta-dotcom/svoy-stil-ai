# OUTFIT-05 — контекст образа

Статус: **PASS для продуктового и reasoning-контракта; HOLD для заявления о полной runtime-поддержке**  
Область: только личный гардероб пользователя  
Принципы: local-first, explicit/confirmed-only, unknown-safe, без публичного score

## 1. Цель и границы

Контекст отвечает на практический вопрос: «Можно ли предложить этот комплект для явно заданных условий и какой безопасный запасной вариант дать, если нельзя?». Он включает повод, dress code, погоду, время на ногах, транспорт и явно указанные требования к комфорту.

Контекст не распознаёт человека или вещи по фотографии, не выводит параметры тела, здоровье, возраст, пол, доход, профессию или демографические признаки. Он не обращается к магазинам и не предлагает покупку как обязательный fallback. Источник вещей — только подтверждённый личный гардероб текущего owner scope.

Demo-каталог и personal wardrobe не смешиваются:

- personal-запрос ранжируется только по personal items пользователя;
- demo-образ может использовать только demo items и должен иметь явную маркировку `mode: demo`;
- demo-результат нельзя сохранять как личный образ или использовать для обучения персонального профиля без отдельного явного действия пользователя;
- отсутствие подходящей вещи в personal wardrobe не разрешает молча подмешать demo или retail item.

## 2. Источники правды и подтверждение

В reasoning допускаются только поля с явным provenance и подтверждением:

1. пользователь ввёл или подтвердил контекст;
2. вещь и её релевантные свойства находятся в личном гардеробе и подтверждены;
3. погодные данные, если загружены, показаны пользователю с местом и временем наблюдения и подтверждены перед применением;
4. сохранение контекста выполняется только по отдельному consent; без consent контекст живёт в памяти текущей сессии.

Черновик, ошибка загрузки, просроченная погода, неподдерживаемое enum-значение, `null`, отсутствие поля или `confirmed !== true` трактуются как unknown. Unknown не превращается в «подходит», но сам по себе не создаёт hard conflict: система либо задаёт короткий уточняющий вопрос, либо выдаёт условный вариант с раскрытым ограничением.

Минимальный provenance для применённого факта: `source` (`manual | weather`), `confirmed: true`, `observedAt` для внешней погоды, версия mapping/ruleset. Точные координаты и история перемещений не нужны и не должны сохраняться.

## 3. Канонический вход OUTFIT-05

Поля ниже — целевой нормализованный контракт. Текущий runtime `context.v1` поддерживает только подмножество, отмеченное в разделе 8.

| Блок | Поля | Правило |
|---|---|---|
| Повод | `occasion`, `activity` | Свободный текст нормализуется только после подтверждения; неизвестная формулировка остаётся unknown. `activity`: `low | moderate | active`. |
| Dress code | `minFormality`, `maxFormality?`, `excludedOccasions?`, явные `required`/`forbidden` свойства | Числовая шкала допустима только при единой версии taxonomy. Явное «обязательно/нельзя» важнее предпочтений. |
| Погода | `temperatureC`, `feelsLike`, `precipitation`, `wind`, `indoorOutdoor`, `exposureMinutes`, `observedAt` | `temperatureC`: −60…60. Осадки: `none | rain | snow | mixed`; ветер: `calm | breezy | strong`. Для решения используются только подтверждённые свойства вещей. |
| Нагрузка | `walkingMinutes`, `standingMinutes`, `activity` | Минуты: целое 0…720. Стояние и ходьба хранятся отдельно. |
| Транспорт | `transport`: `walk | public | car | taxi | bicycle | mixed | unknown`, `transfers?`, `outdoorTransferMinutes?` | Транспорт уточняет нагрузку и погодную экспозицию, но не заменяет явно введённые минуты. `mixed` требует деталей или остаётся unknown-safe. |
| Комфорт | `priority`, `requiredComfort`, `avoid`, `mobilityRequirement?` | `priority`: `balanced | comfort | expressiveness`. Только `required`/`avoid` создают hard constraint; обычное предпочтение — soft. |

Контекст и снимок комплекта передаются отдельно. Контекст не должен изменять метаданные вещи. Для проверки нужны подтверждённые outfit/shoes facts: диапазон температуры, формальность, исключённые поводы, мобильность, защита от осадков/ветра и комфорт обуви для ходьбы/стояния. Отсутствующие свойства остаются unknown.

## 4. Hard constraints

Hard constraint — проверяемая причина исключить кандидат до любого ранжирования. Score, вкус, цветовая гармония или популярность вещи не могут его компенсировать.

Hard разрешён только при конфликте двух подтверждённых фактов либо при явном требовании пользователя:

- формальность комплекта ниже явно заданного минимума;
- повод явно находится в `excludedOccasions` комплекта/вещи;
- подтверждённая температура ниже/выше подтверждённого диапазона комплекта;
- долгая ходьба (`walkingMinutes >= 30`) и подтверждённо низкий walking comfort обуви;
- активный повод и подтверждённо ограниченная мобильность комплекта;
- явно обязательное свойство отсутствует либо явно запрещённое присутствует;
- подтверждённые осадки/сильный ветер конфликтуют с явно обязательной защитой и подтверждёнными свойствами комплекта;
- транспорт или маршрут создаёт подтверждённую нагрузку, несовместимую с явным обязательным уровнем комфорта/мобильности.

Последние три пункта — целевое расширение: до реализации отдельных версионированных rules их нельзя эмулировать свободным текстом.

Hard-результат обязан содержать стабильный `code`, `ruleVersion`, точный `evidence` и машинное constraint-условие. В пользовательском ответе показывается конкретная причина и действие, но не числовой score.

## 5. Soft constraints

Soft constraint улучшает порядок допустимых кандидатов и не блокирует образ:

- долго стоять (`standingMinutes >= 60`), а standing comfort обуви подтверждён как средний — предпочесть высокий;
- comfort-first — предпочесть подтверждённо мягкие, свободные, устойчивые варианты;
- много пересадок, лестниц или коротких пеших отрезков — предпочесть мобильность и walking comfort;
- часть события на улице — предпочесть съёмный слой и погодный запас;
- dress code задан как пожелание, а не минимум/запрет;
- пользователь просит баланс выразительности и комфорта без обязательного свойства.

Soft-правило применяется только к подтверждённым данным. Отсутствие comfort tag не означает дискомфорт и не должно давать скрытый штраф, выглядящий как установленный факт.

## 6. Порядок решения

1. Проверить owner scope и режим `personal | demo`; при несоответствии остановить сборку кандидата.
2. Нормализовать только подтверждённые поля, остальные оставить unknown.
3. Построить кандидаты только из доступных подтверждённых вещей нужного scope.
4. Применить hard constraints. Кандидат с hard conflict исключить без score-компенсации.
5. К оставшимся применить soft preferences детерминированно; использовать стабильный tie-break.
6. Вернуть до трёх вариантов с фактами, компромиссами и уровнем уверенности (`high | medium | low`), но без публичного числа или вероятности «подойдёт».
7. Если данных мало или все кандидаты исключены, выполнить fallback из следующего раздела.

## 7. Fallback и abstention

Fallback всегда остаётся внутри personal wardrobe и не выдумывает свойств.

При hard conflict система последовательно пытается:

1. заменить только конфликтующий элемент на подтверждённую вещь того же назначения;
2. добавить/убрать подтверждённый слой, если это устраняет погодный конфликт;
3. сохранить остальной комплект и заменить обувь при конфликте ходьбы/стояния;
4. предложить пользователю ослабить только явно названное условие (`adjust_request`), не меняя его молча;
5. если безопасной подтверждённой альтернативы нет — abstain: «В личном гардеробе нет подтверждённого варианта под эти условия» и перечислить, какого свойства или уточнения не хватает.

Для unknown применяются не hard rejection, а минимальный следующий шаг:

- неизвестен повод/dress code — спросить о минимальной формальности или явных запретах;
- неизвестна погода — попросить подтвердить температуру/осадки или обозначить рекомендацию как условную;
- неизвестны ходьба, стояние или транспорт — спросить один объединённый вопрос о нагрузке;
- неизвестен comfort вещи — не обещать комфорт; предложить примерку или подтверждённую альтернативу;
- внешний weather fetch недоступен — сохранить ручной local-first путь, не подставлять старые/предполагаемые данные.

Допустимый fallback-copy: «Подтверждённых данных недостаточно, чтобы гарантировать комфорт. Вариант условный: проверьте обувь для 60 минут стояния». Недопустимо: «Этот образ точно удобный», «подойдёт на 92%», «у вас такой тип фигуры».

## 9. Приёмка OUTFIT-05

Документ считается принятым, если реализация доказывает fixtures/tests для следующих классов:

- каждый hard rule: positive conflict, boundary, unknown/partial, unconfirmed input;
- каждый soft rule не исключает кандидата;
- transport `mixed/unknown` не создаёт выдуманной нагрузки;
- weather stale/error использует manual fallback и не применяет неподтверждённые значения;
- personal/demo cross-scope candidate отклоняется;
- all-hard-rejected приводит к abstention, а не к ослаблению запрета;
- replacement сохраняет anchor и все остальные hard constraints;
- explanations содержат только evidence codes и не показывают score/вероятность;
- контекст не сохраняется без consent, очистка удаляет локальную запись;
- неизвестные и будущие enum/version значения fail closed или ignored-as-unknown согласно границе, но не принимаются как подтверждённая совместимость.

До закрытия HOLD-пунктов в разделе 8 продукт может честно заявлять поддержку подтверждённых правил `context.v1`, но не «полный учёт транспорта, dress code и погоды».

## 10. Зависимости

- versioned schema/mapping для расширенного Context;
- UI-поля: walking, transport, indoor/outdoor/exposure, обязательные comfort/dress-code ограничения;
- подтверждение и freshness policy для weather snapshot;
- подтверждённые garment facts для weather protection, mobility и shoe comfort;
- новые versioned context rules + allowlist/message keys + deterministic fixtures;
- candidate/fallback orchestration, сохраняющий owner scope, anchor и hard constraints;
- privacy tests для consent, local storage, clear и отсутствия сетевого транспорта персонального контекста.
