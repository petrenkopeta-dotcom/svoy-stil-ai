# Stylist Reasoning: контракт v1

Статус: Stage 1, локальный детерминированный контур  
Версия схемы: `1.0`  
Версия набора правил по умолчанию: `stylist-rules/1.0`

## Границы

Контракт не выполняет распознавание изображений и не вызывает внешние сервисы. Production recognition остаётся **NO-GO**. Признаки ниже являются только редактируемыми данными карточки вещи; они не выводят и не кодируют цветотип, параметры тела, возраст, пол, этничность или другую демографию человека по фотографии.

Runtime-контракт находится в `src/stylistReasoningSchemas.js`, переносимый JSON Schema — в `schemas/stylist-reasoning-v1.schema.json`. Каждая сущность содержит `schema_version` и дискриминатор `kind`. Неизвестная версия отклоняется, поэтому миграция не происходит молча.

## Сущности

- `StylistRequest`: идентификатор запроса, доступные вещи, событие, сезон, явные ограничения и необязательная якорная вещь.
- `GarmentStyleFeatures`: редактируемый снимок признаков вещи с `revision`. Цвета имеют роли `dominant`, `supporting`, `accent`; также хранятся светлота, насыщенность, температура, принт, фактура, посадка, объём, длина, формальность, сезонность, тепло и акцентность.
- `CandidateOutfit`: состав кандидата и версия детерминированного генератора.
- `ReasoningFact`: атомарный объяснимый результат правила. `rule_id` + `rule_version`, outcome, вес, ключ сообщения и список evidence позволяют воспроизвести объяснение без свободного provider-текста.
- `ScoredRecommendation`: кандидат, нормированный score 0..100, уровень, факты, альтернативы и версия ruleset.
- `AlternativeAction`: структурированное действие `replace`, `remove`, `add` или `adjust_request`, связанное с фактами.

## Безопасные значения по умолчанию

Неизвестное не превращается в уверенное предположение: категориальные признаки получают `unknown`, сезон — `all_season`, числовые шкалы вещи — нейтральное значение `3`, lightness/saturation — `0.5`, score и вес факта — `0`. Пустой кандидат запрещён. Диапазоны и taxonomy проверяются до использования.

## Совместимость

Taxonomy категорий, стилей, сезонов, принтов, силуэтов и длин совпадает с `clothing-item-analysis.schema.json`. `garmentFeaturesFromLegacyCard(card)` принимает старые поля `id`, `type`, `color`, `style_tags`, `seasons`, `formality`, `warmth`, `pattern`, `silhouette`, `length`. Старый `silhouette` становится `fit`; одиночный `color` становится dominant-цветом. Если старая карточка не содержит hex, адаптер использует нейтральный `#808080` как явный placeholder, а неизвестная категория остаётся `unknown`.

## Версионирование и round-trip

`serializeStylistEntity` сначала повторно валидирует объект, затем сериализует JSON. `deserializeStylistEntity` выбирает валидатор только по allowlisted `kind`. Round-trip сохраняет каноническое представление. Любое несовместимое изменение полей, шкал или семантики требует новой `schema_version`; изменение правил оценки — новой `ruleset_version`/`rule_version` без обязательного изменения схемы.

## Вход следующего этапа

Детерминированному reasoning engine нужны: один `StylistRequest`, набор подтверждённых `GarmentStyleFeatures`, каталог версионированных правил и стабильные message keys. Выход должен состоять только из `ScoredRecommendation` с трассируемыми `ReasoningFact` и `AlternativeAction`.
