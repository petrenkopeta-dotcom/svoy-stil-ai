# OUTFIT-07 — разнообразие трёх вариантов

Статус документа: **PASS (контракт готов)**  
Статус runtime-интеграции: **HOLD до отдельной реализации и тестов**  
Область: только личный гардероб пользователя; локальный детерминированный контур.

## 1. Цель и продуктовый контракт

Генератор возвращает до трёх пригодных комплектов с разными, заранее понятными ролями:

1. `calm` — наиболее спокойный и предсказуемый;
2. `balanced` — базовый выбор с умеренным отличием;
3. `accent` — наиболее выразительный из безопасных доступных вариантов.

Роли описывают относительное различие **внутри текущего набора подтверждённых вещей**, а не объективное качество, вкус пользователя или свойства человека. Они не являются публичными score. Если гардероб не позволяет честно собрать три различающихся комплекта, результат содержит меньше трёх вариантов и стабильный reason code; система не придумывает вещи или признаки.

## 2. Жёсткие границы

- Источник кандидатов — только `ready`-вещи personal wardrobe текущего локального профиля.
- Demo-каталог и demo-history не смешиваются с personal wardrobe и personal history. Режим определяется до генерации и переносится в историю как `scope: personal | demo`.
- Не выполняются внешние retail/provider-вызовы; отсутствующие категории не дополняются товарами из магазина.
- Не используются и не выводятся цветотип, параметры тела, возраст, пол, этничность и иные чувствительные или неподтверждённые признаки.
- `unknown` остаётся `unknown`: неизвестная выразительность, цвет, принт или формальность не дают кандидату положительный либо отрицательный факт без отдельного подтверждённого правила.
- Числовые utility, novelty, distance и внутренние штрафы остаются внутренней трассировкой. В UI разрешены роль, состав, краткое объяснение и reason codes, но не публичный score.
- История локальна по умолчанию, минимальна, очищаема вместе с локальными данными профиля и не содержит фото, свободный пользовательский текст или внешние идентификаторы.

## 3. Вход и нормализация

Минимальный вход:

```text
DiversityRequest {
  requestId
  scope: personal | demo
  eligibleGarments[]
  anchorId?: garmentId
  recentHistory[]
  context: confirmed occasion/weather/preferences only
  limit: 3
}
```

Перед отбором:

1. применить hard constraints и собрать только структурно полные кандидаты;
2. исключить неготовые, запрещённые и недоступные вещи;
3. при `anchorId` оставить только кандидаты, содержащие этот ID;
4. канонизировать `signature` как отсортированный список уникальных garment ID;
5. удалить кандидаты с одинаковой `signature`;
6. стабильно сортировать равные результаты по `signature`.

Любая история с другим `scope`, несовместимой версией схемы, отсутствующей подписью или некорректной датой игнорируется безопасно. Некорректная история не должна блокировать генерацию.

## 4. Anchor invariants

Anchor — hard constraint, а не сигнал ранжирования.

- Если `anchorId` задан и существует среди eligible-вещей, **каждый** возвращённый вариант содержит anchor ровно один раз.
- Anchor запрещено заменять ради novelty, роли `accent` или устранения дубля.
- Разнообразие считается только по неякорным вещам: общий anchor не делает два варианта дублями сам по себе.
- Если anchor отсутствует во входном гардеробе: ноль вариантов, `anchor_not_found`.
- Если anchor существует, но не eligible: ноль вариантов, `anchor_unavailable`.
- Если с anchor нельзя собрать полный комплект: ноль вариантов и структурные причины (`missing_shoes`, `missing_outfit_base`, `missing_required_outerwear`), при необходимости вместе с `anchor_incomplete`.
- После каждого этапа отбора выполняется invariant-check. Нарушивший anchor кандидат удаляется; нарушение всего результата закрывает выдачу кодом `anchor_invariant_violation`, а не молчаливой заменой.

## 5. Модель различия

Для пары кандидатов `A`, `B` вычисляются только внутренние признаки:

- `exactDuplicate`: равенство канонических signature;
- `nonAnchorOverlap`: доля общих неякорных garment ID относительно большего неякорного состава;
- `categoryChange`: количество обязательных категорий, где изменился garment ID;
- `optionalChange`: изменение outerwear/accessory;
- `styleDistance`: различие только по подтверждённым категориальным признакам цвета, силуэта, принта, формальности и accentness; `unknown` не считается различием.

Near-duplicate — пара, у которой нет изменения обязательной категории и меняется только необязательный аксессуар/слой, либо `nonAnchorOverlap >= 0.75`. Порог и формула версионируются (`outfit-diversity/1.0`). Exact duplicates запрещены всегда. Near-duplicates запрещены, пока существует пригодный кандидат вне этого класса.

## 6. Детерминированный алгоритм calm / balanced / accent

Сначала основной candidate engine формирует pool и вычисляет внутреннюю utility пригодности. Diversity не может вернуть кандидата, отфильтрованного hard constraints.

### 6.1 Calm

Выбрать пригодный кандидат с максимальной базовой utility среди кандидатов с минимальной подтверждённой выразительностью. Подтверждённая выразительность учитывает accentness, контраст, принт и число необязательных акцентных элементов. При отсутствии этих данных выбор сводится к базовой utility и стабильному tie-breaker; неизвестные признаки не трактуются как спокойные.

### 6.2 Balanced

Из оставшихся выбрать кандидат, который:

1. не является exact/near-duplicate `calm`, если существует иной пригодный кандидат;
2. меняет хотя бы одну неякорную обязательную вещь, когда pool это позволяет;
3. максимизирует `baseUtility - historyPenalty + diversityGain`, сохраняя стабильный tie-breaker.

`diversityGain` ограничен: он не может сделать непригодный или заметно более слабый по hard/confirmed context кандидат победителем.

### 6.3 Accent

Из оставшихся выбрать наиболее выразительный **подтверждёнными данными** пригодный кандидат, который не является near-duplicate уже выбранных, пока доступна альтернатива. Предпочтительный порядок отличий: замена неякорной обязательной вещи; затем изменение силуэтной/цветовой схемы; затем верхний слой; затем аксессуар. Простое добавление аксессуара к идентичной базе — последняя деградация, а не полноценный accent-вариант.

Если подтверждённых признаков выразительности нет, роль означает только «наиболее отличающийся доступный вариант». Объяснение не должно утверждать, что он яркий, контрастный или акцентный; используется нейтральный текст «самый отличающийся из доступных».

## 7. Anti-duplicates внутри ответа

Отбор идёт последовательно `calm → balanced → accent` с пересчётом штрафа после каждого выбора.

- Одинаковая signature никогда не возвращается дважды.
- Для комплектов `top + bottom + shoes` предпочтительно различие минимум в одной из этих категорий; для `dress/one_piece + shoes` — в платье/комбинезоне или обуви.
- При anchor требование относится к остальным обязательным категориям.
- Кандидат, отличающийся только порядком вещей, считается exact duplicate.
- Кандидат, отличающийся только неизвестным/неподтверждённым признаком, не получает diversity credit.
- Если избежать near-duplicate нельзя, допускается один такой вариант только после исчерпания альтернатив и с `degradedReason: insufficient_distinct_candidates`.

## 8. Recent-history

`recentHistory` хранит минимальные записи:

```text
{ signature, shownAt, scope, engineVersion, anchorId? }
```

Политика v1:

- учитывать последние 20 валидных показов либо 30 локальных дней, что меньше;
- точное совпадение с недавней signature получает максимальный history penalty;
- повтор отдельных вещей получает меньший penalty, пропорциональный non-anchor overlap;
- совпадение anchor при anchor-flow не штрафуется;
- более свежая запись штрафует сильнее, одинаковые записи схлопываются по наиболее свежей дате;
- history penalty — soft constraint и никогда не отменяет hard constraints, anchor или полноту комплекта;
- если без повторов нельзя вернуть пригодный результат, разрешён повтор с `degradedReason: recent_history_exhausted`;
- удалённые garment ID можно оставить только внутри непрозрачной signature до истечения окна; история не должна восстанавливать карточку удалённой вещи.

История влияет на выбор, но не на фактические объяснения совместимости. Нельзя говорить «вы давно это не носили», потому что история показов не равна истории носки.

## 9. Деградация и reason codes

Возвращается `0..3` вариантов. Роль сохраняет порядок, но не требует заполнения любой ценой.

| Ситуация | Результат |
|---|---|
| Нет пригодного полного кандидата | `[]` + существующие structural reason codes |
| Есть один уникальный кандидат | только `calm` + `insufficient_distinct_candidates` |
| Есть два уникальных кандидата | `calm`, `balanced` + `insufficient_distinct_candidates` |
| Три есть только с near-duplicate | третий допустим как деградация; reason code обязателен |
| Все уникальные кандидаты недавно показаны | лучший повтор; `recent_history_exhausted` |
| Выразительность неизвестна | роли остаются, фактическое accent-утверждение запрещено |
| История повреждена/чужого scope | игнорировать историю; `history_ignored` только во внутренней диагностике |

Порядок публичных reason codes стабилен. Технические исключения и внутренние числа в UI не выводятся.

## 10. Выход

```text
DiversityResult {
  engineVersion: "outfit-diversity/1.0"
  variants: [
    { role: calm | balanced | accent, signature, items[], explanationKey, degradedReason? }
  ]
  noCandidateReasons[]
}
```

Публичное объяснение строится из подтверждённых фактов и состава комплекта. Поля `baseUtility`, `historyPenalty`, `diversityGain`, pairwise distance и numeric accentness в публичный объект не входят.

## 11. Детерминизм и порядок tie-break

При одинаковом входе, версии правил и history результат должен быть byte-stable по ролям и signature. Порядок сравнения: итоговая внутренняя utility; меньший recent-history penalty; большее допустимое отличие; каноническая signature по возрастанию. Текущее время передаётся как фиксированный `asOf`, а не читается внутри цикла отбора.

## 12. Acceptance / QA gate

Runtime-реализация получает **PASS**, только если автоматические тесты подтверждают:

1. три роли и стабильный порядок на достаточном гардеробе;
2. отсутствие exact duplicates и приоритет не-near-duplicates;
3. различие хотя бы одной неякорной обязательной вещи, когда такое решение существует;
4. anchor присутствует в каждом результате во всех трёх ролях;
5. anchor не штрафуется recent-history и никогда не заменяется;
6. точная recent-signature отодвигается при наличии сопоставимой альтернативы;
7. повтор разрешается при исчерпании pool и сопровождается reason code;
8. повреждённая, просроченная и cross-scope history безопасно игнорируется;
9. personal/demo наборы и histories не пересекаются;
10. `unknown` не создаёт фактических утверждений или искусственного diversity;
11. выдача 0/1/2 вариантов корректна и не дополняется выдуманными вещами;
12. публичный результат не содержит числовых score и внутренних штрафов;
13. перестановка входного wardrobe не меняет результат;
14. одинаковый `asOf` даёт идентичный результат;
15. все hard constraints проверяются для каждого возвращённого варианта, а не только top-1.

Рекомендуемый golden-набор: обычный personal wardrobe; anchor top; anchor shoes; один полный комплект; два уникальных комплекта; accessory-only различие; все варианты в recent history; неизвестные признаки; demo/personal одинаковые ID; удалённая вещь в history.

## 13. Evidence и зависимости

Существующая база, на которую опирается контракт:

- `src/stylistCandidateEngine.js`: hard constraints применяются до ранжирования, anchor фильтрует каждый generated set, exact signatures дедуплицируются, `selectDiverse` штрафует повтор вещей;
- `src/stylistCandidateEngine.test.js`: уже проверяются anchor invariant, детерминизм, отсутствие числового score и базовое diversity;
- `src/outfitEngine.js`: history exact-signatures сейчас только отодвигаются после candidate engine;
- `docs/stylist-candidate-engine-v1.md`: закреплены локальный детерминированный candidate pool, стабильный tie-break и непубличность ranking trace;
- `docs/stylist-reasoning-contract-v1.md`: закреплены unknown-safe defaults и использование подтверждённых признаков.

Зависимости для runtime-этапа:

1. версионированная реализация selector `outfit-diversity/1.0` поверх candidate pool;
2. локальный namespaced history store с явным `scope` и очисткой;
3. адаптер UI для ролей и reason codes без numeric scores;
4. unit/golden/integration тесты из QA gate;
5. согласование порога «заметно более слабого» кандидата как внутренней versioned-константы без публикации score.

## 14. Риски и решение gate

- Текущий `selectDiverse` оптимизирует общий reuse, но не гарантирует смысловые роли calm/balanced/accent и отдельное изменение обязательной категории.
- Текущий `outfitEngine` учитывает только точное совпадение history и не ограничивает окно, scope или повтор отдельных вещей.
- Если expressive-признаки неполны, роль `accent` легко превратить в недоказанное утверждение; поэтому контракт требует нейтральной деградации.
- Малый гардероб неизбежно даёт повторяемость; корректное поведение — честные 1–2 варианта или маркированная деградация.

Итог: **PASS** для документа и границ OUTFIT-07; **HOLD** для заявления о готовой runtime-функции до реализации зависимостей и прохождения QA gate.
