# CAPSULE-01 — продукт и end-to-end CJM AI-капсул

**Статус:** продуктовый контракт — **PASS**; production implementation / release — **HOLD**  
**Дата:** 21 августа 2026  
**Scope:** капсула из личного гардероба; сезон / поездка / офис; опциональное точечное докупание. Авторизация и Supabase вне scope. VK ID — только исследовательский backlog. Production-код не изменялся.

## 1. Решение

Запускать AI-капсулу как управляемый сценарий поверх **личного** гардероба: пользователь задаёт задачу и ограничения, система проверяет покрытие категорий, предлагает компактный набор вещей и воспроизводимые образы, объясняет пробелы и только затем предлагает не более нескольких точечных докупок. Покупка не является условием успеха: пользователь может отказаться, заменить покупку своей вещью, ослабить условия или сохранить честно ограниченную капсулу.

Капсула — не просто список вещей. Результат обязан содержать:

- цель и период;
- выбранные вещи из personal wardrobe;
- набор технически полных образов;
- покрытие дней/сценариев и известные ограничения;
- необязательный список пробелов и точечных докупок;
- явную версию/снимок результата, чтобы он не менялся молча вслед за гардеробом.

**PASS для product discovery и UX specification:** сценарий согласуется с существующими wardrobe, candidate engine, shopping-anchor, weather, learning и privacy-контрактами.

**HOLD для production:** нет capsule domain contract/repository/UI; не определены entitlement-различия тарифов 499/999 ₽; текущий candidate engine не оптимизирует капсулу как набор и не доказывает покрытие дней; production photo recognition остаётся HOLD; auth/Supabase нельзя использовать как скрытую зависимость этой задачи.

## 2. Неподвижные продуктовые границы

1. **Personal only.** Сохранённая капсула строится только из `source=personal`. Demo можно использовать лишь как маркированный пример до личного сценария; demo и personal нельзя смешивать или сохранять вместе.
2. **Покупка временная.** Кандидат на покупку имеет `source=shopping_pending`, участвует в preview, но не попадает в гардероб до отдельного подтверждения. Отмена удаляет временный anchor без побочных записей.
3. **Фото privacy-first.** До разрешённого privacy decision изображение не уходит в сеть. Ручная декларация «отдельная вещь без человека» означает review, а не production-recognition. Отказ от фото оставляет ручное добавление.
4. **Честная комплектность.** Базовый полный образ: `top + bottom + shoes` или `dress/one_piece + shoes`; верхняя одежда и аксессуар добавляются по контексту. При нехватке категорий система не изображает готовность.
5. **Погода опциональна.** Для сезона/поездки достаточно ручного города/диапазона условий либо режима «без погоды»; точная геолокация и фоновой GPS не нужны.
6. **Без чувствительных выводов.** Не собирать и не выводить пол, возраст, параметры тела, цветотип или демографию. Посадка и температурный комфорт — явные пользовательские предпочтения.
7. **Core before paywall.** Цена не показывается до понятного preview пользы. Интерфейс сообщает entitlement, что расходует лимит и дату сброса без искусственной срочности.
8. **Тарифы без выдумки.** 499/999 ₽ отображаются как текущий продуктовый контекст, но различия между ними — HOLD до решения владельца продукта. Известны только общий стартовый ориентир 50 вещей и последующее пополнение 10–15 вещей/мес.; точные правила server-owned и не должны вычисляться из local counters.

## 3. Объект и состояния капсулы

Минимальный будущий `CapsuleV1`:

| Поле | Смысл |
|---|---|
| `id`, `schema_version`, `created_at`, `updated_at` | стабильность и миграции |
| `source_scope=personal` | запрет demo/personal mixing |
| `objective` | `season`, `trip`, `office` |
| `period` | даты либо сезон; для офиса — рабочие дни/частота |
| `context` | occasion, dress code, ручной weather mode, laundry cadence, багаж/максимум вещей |
| `item_snapshots[]` | снимки личных вещей в момент сохранения |
| `outfit_snapshots[]` | воспроизводимые полные образы и назначение |
| `coverage` | покрытые/непокрытые дни, сценарии и причины |
| `gaps[]` | категория, необходимость, причина, допустимые замены |
| `shopping_candidates[]` | только временные или отдельно подтверждённые ссылки; не товары магазина |
| `status` | `draft`, `ready`, `limited`, `saved`, `archived` |
| `engine_versions` | генератор, ranking weights, правила покрытия |

Состояния: `start → context → inventory_check → generate → review → saved`. Ветки `insufficient_inventory → add_own | preview_purchase | relax | save_limited | exit`; ветка покупки `shopping_pending → matched → save_confirmation → saved | discarded`.

## 4. Главный end-to-end CJM

| Этап | Пользователь | Интерфейс / система | Успешный выход |
|---|---|---|---|
| 1. Вход | Нажимает «Собрать капсулу» из личного гардероба | Показывает 3 цели: сезон, поездка, офис; кратко обещает результат | Выбрана одна цель |
| 2. Контекст | Задаёт период и только нужные ограничения | Прогрессивные поля; можно «без погоды»; объясняется, зачем нужен каждый ввод | Валидный capsule brief |
| 3. Инвентарь | Подтверждает вещи/исключения | Анализируются только personal items; показываются количество, категории, неподтверждённые данные | Понятная readiness-карточка |
| 4. Пробелы | Решает добавить свою вещь, посмотреть докупку, ослабить условия или продолжить с ограничениями | Называются конкретные отсутствующие категории и эффект каждой | Нет тупика и скрытой покупки |
| 5. Генерация | Ждёт и при необходимости корректирует | Детерминированно строятся полные образы; показывается честное покрытие и версии | Есть хотя бы один полный образ либо `limited` с причиной |
| 6. Review | Закрепляет/исключает вещи, заменяет образ, отмечает «не моё» | Пересчитывает только затронутую часть, сохраняет явные реакции без чувствительных inference | Пользователь понимает состав и компромиссы |
| 7. Докупка | Опционально проверяет одну недостающую вещь | Вещь временная; сочетания только с personal wardrobe; сохранение — отдельное подтверждение | Покупка принята, заменена или отклонена |
| 8. Сохранение | Сохраняет капсулу | Создаётся snapshot вещей и образов; показывается статус persistence | Результат воспроизводим после reload |
| 9. Использование | Открывает капсулу в день/поездке/офисе | Видит подходящий образ, погоду при разрешённом режиме, доступные замены | Можно использовать без повторной генерации |
| 10. Возврат | Обновляет период/вещи или архивирует | Предлагается «обновить копию», а не молча мутировать сохранённую капсулу | История и исходный snapshot сохранены |

## 5. Варианты цели

### 5.1 Сезон

Обязательное: сезон или даты, типичные occasion. Опционально: город/ручной диапазон погоды, чувствительность к холоду, частота стирки, максимальное число вещей. Результат показывает покрытие температурных/осадочных режимов только при наличии соответствующих подтверждённых данных. Если верхняя одежда нужна по погоде, её отсутствие — gap, а не молчаливый пропуск.

### 5.2 Поездка

Обязательное: даты, длительность, основные активности; опционально — город, dress code, багажный лимит, доступ к стирке. Оптимизация: минимальное число вещей при максимуме повторно комбинируемых полных образов. Нельзя обещать «образ на каждый день», если дни или сценарии не покрыты; в результате явно видны непокрытые слоты.

### 5.3 Офис

Обязательное: dress code, число офисных дней в неделю, период; опционально — commute/weather и желаемая повторяемость. Результат различает техническую полноту и соответствие офисному контексту. Повторы разрешены и объясняются; «не повторять верх два дня подряд» — пользовательское ограничение, а не скрытая норма.

## 6. Обязательные ветки пользователей

### Новый пользователь

Если личного гардероба ещё нет, CTA «Собрать капсулу» ведёт не в пустой генератор, а в короткий путь:

1. Маркированный demo-preview объясняет результат без сохранения.
2. CTA «Начать с моей вещи» открывает personal intake.
3. После локального privacy gate пользователь добавляет вручную/по фото первую вещь.
4. При одной вещи система запускает ветку «1 вещь», не обещая готовую капсулу.

Auth/Supabase не проектируются здесь. Текущий local/personal runtime и целевой auth-контур противоречат друг другу по моменту personal writes; интегратор обязан выбрать действующий release policy отдельным решением, не обходить gate внутри capsule UI.

### Возвращающийся пользователь

Показываются последние сохранённые капсулы и CTA «Новая капсула». Если сохранённый snapshot ссылается на удалённую/изменённую вещь, исходный результат остаётся читаемым, а интерфейс предлагает «Создать обновлённую копию». При storage failure не показывать ложное «сохранено»; оставить draft в памяти с retry/export-safe guidance.

### В гардеробе 1 вещь

Система использует её как anchor, определяет недостающие категории и предлагает четыре равноправных выхода: добавить свою вещь, проверить точечную докупку, посмотреть demo-пример отдельно, завершить. Статус — `limited`, пока нет хотя бы одного полного образа. Demo-вещи не подмешиваются в personal result.

### В гардеробе 10 вещей

Сначала проверяется не число, а категорийное и контекстное покрытие. Если возможны полные образы — генерируется компактная капсула из доступного набора, показываются повторное использование и coverage. Если 10 вещей принадлежат неподходящим/одинаковым категориям, включается ветка недостатка; количество само по себе не означает readiness.

### Недостаточно категорий

Показывается стабильная причина: например, «не хватает обуви» или «нужен верх и низ либо платье». Для каждой gap-категории доступны:

- выбрать неправильно классифицированную свою вещь и исправить категорию;
- добавить свою вещь вручную/по фото;
- временно проверить одну потенциальную покупку;
- ослабить конкретный контекст;
- сохранить ограниченный draft или выйти без потери гардероба.

Нельзя выдавать частичный комплект за образ, скрывать gap или отправлять прямо в paywall.

### Отказ от покупки

«Не покупать» — нормальный успешный исход. Временный shopping anchor удаляется, гардероб и сохранённая капсула не меняются. Система предлагает: заменить вещью из гардероба, сократить покрытие, ослабить ограничение или сохранить список пробелов на потом. Никаких повторных pressure-модалок в текущей сессии.

## 7. Точечное докупание

Предлагать докупку только если конкретная gap-категория увеличивает измеримое покрытие. До интеграции каталога это **не marketplace и не рекомендация конкретного SKU**: пользователь вручную описывает или добавляет фото рассматриваемой вещи, получает совместимость с личным гардеробом и объяснение.

Правила:

- максимум 1 primary gap за шаг; после решения пересчитать покрытие;
- показать «с чем сочетается» и «какие сценарии закрывает»;
- не заявлять посадку/размер/качество/наличие/цену без соответствующих данных;
- `shopping_pending` не расходует wardrobe quota и не сохраняется автоматически;
- после явного «Купила/купил — добавить» запросить подтверждение карточки и только тогда создать personal item;
- отказ/закрытие полностью обратимы.

## 8. Тарифы 499/999 ₽

### PASS

- Первая доказанная польза и preview капсулы предшествуют продаже.
- UI может показывать 499/999 ₽ только вместе с текущим entitlement, правилами лимита и датой сброса.
- Capsule UX готов к server-owned `quota_used`, `quota_limit`, `quota_reset_at` и entitlement code.

### HOLD

До запуска владелец продукта должен зафиксировать в одном contract/decision record:

1. Что именно различает 499 и 999 ₽: число активных/сохранённых капсул, генерации, planning, weather, Objective V3 beta или иное.
2. Что считается вещью и расходует стартовые 50; расходует ли подтверждённая покупка лимит (рекомендуется: да, после personal save), а temporary anchor (рекомендуется: нет).
3. Точные 10 или 15 вещей/мес. для каждого тарифа, момент/часовой пояс сброса и перенос остатка.
4. Поведение downgrade, истёкшей подписки, offline и недоступного entitlement service.
5. Какие core-действия всегда остаются доступны: чтение/экспорт/удаление своих данных и отказ от покупки не могут блокироваться paywall.

Не фиксировать различия тарифов в capsule UI или local storage до этого решения.

## 9. Privacy, данные и аналитика

- Капсулы private-by-default; публичного профиля/шеринга в V1 нет.
- Фото, имена файлов, EXIF, item payload и свободный текст не попадают в аналитику.
- Допустимые события: `capsule_started(objective)`, `inventory_checked(coverage_bucket)`, `capsule_generated(outcome, outfit_count_bucket)`, `gap_shown(category_code)`, `shopping_preview_started`, `shopping_declined`, `capsule_saved(outcome)`. Только allowlist enum/buckets, coarse timestamp и opaque local/session correlation.
- Погода: ручной город или coarse location по отдельному разрешению; raw GPS не хранится.
- Feedback явный и сбрасываемый; не выводить чувствительные характеристики.
- Export/delete должны включать будущие capsule snapshots и связи с фото; удаление капсулы не должно молча удалять вещи гардероба.

## 10. Риски и меры

| Риск | Приоритет | Мера / gate |
|---|---:|---|
| Красивый, но неполный набор выдаётся за капсулу | P0 | Coverage contract + no-candidate reasons + `limited` status |
| Demo/personal или shopping/personal смешиваются | P0 privacy | Source guards на domain commands; negative tests; snapshot audit |
| Временная покупка сохраняется без подтверждения | P0 data | `shopping_pending` + отдельный `requestSave/confirmSave`; cancel/discard tests |
| Тарифы обещают незафиксированные возможности | P0 commercial | Entitlement decision record до UI/build |
| Фото уходит в сеть до consent | P0 privacy | Existing local intake gate; network-before-consent=0 browser gate |
| Auth-policy обходится новым capsule route | P0 security | Отдельный screen/action policy; capsule не меняет auth/Supabase |
| 10 вещей создают ложную readiness | P1 product | Считать category/context coverage, не item count |
| Snapshot дрейфует после правок гардероба | P1 data | Immutable item/outfit snapshots; update-as-copy |
| Сезон/поездка обещают точную погоду | P1 trust | Указывать источник/дату/режим; fallback «без погоды» |
| Алгоритм повторяет вещи или слишком велик pool | P1 UX/perf | Diversity policy, capsule limits, deterministic budget/perf gate |
| Докупка превращается в давление/affiliate bias | P1 trust | Равноправный отказ, no repeat pressure, benefit explanation |
| Storage quota/offline даёт ложное сохранение | P1 reliability | Durable read-back, retry state, never claim saved without receipt |

## 11. Зависимости

**Можно переиспользовать:** `stylistCandidateEngine` (полные комплекты, hard constraints, stable reason codes), `outfitEngine` (anchor/missing categories), `shoppingFlowController/state` (temporary candidate and explicit save), local wardrobe repositories, weather context, explicit learning feedback, photo privacy gate.

**Нужно спроектировать/реализовать отдельно:**

- `CapsuleV1`, coverage rules и snapshot repository;
- capsule set optimizer поверх отдельных outfit candidates;
- objective-specific brief и UI;
- entitlement decision/service adapter;
- persistence/export/delete integration;
- shared route/action policy без изменения auth в рамках CAPSULE-01;
- доступный mobile/desktop review и browser QA;
- production recognition — только после отдельного privacy/security gate.

## 12. Acceptance criteria

### Product/UX — PASS, если

- [ ] Доступны ровно три entry goal: сезон, поездка, офис; необязательные вопросы прогрессивны и объяснены.
- [ ] Новый пользователь получает demo-preview отдельно и путь «начать с моей вещи»; demo не записывается как personal.
- [ ] Returning user видит сохранённый snapshot; изменения предлагаются новой копией.
- [ ] Для 1 вещи показываются gap и четыре выхода без ложной готовности.
- [ ] Для 10 вещей readiness зависит от категорий/context, не от количества.
- [ ] Missing categories перечислены стабильными понятными причинами; частичный комплект имеет статус `limited`.
- [ ] Отказ от покупки завершает shopping flow без записи и без повторного давления.
- [ ] Любая докупка показывает измеримое изменение coverage и остаётся `shopping_pending` до подтверждения.
- [ ] Сохранённая капсула воспроизводится после reload независимо от последующих изменений гардероба.
- [ ] Пользователь может работать без погоды, фото и покупки.

### Contract/privacy/data — release HOLD, пока не выполнено

- [ ] Domain guards запрещают demo/personal mixing и неавторизованные personal actions согласно выбранной release policy.
- [ ] Network-before-photo-consent = 0; manual path доступен; production recognition не заявляется.
- [ ] Capsule export/delete, photo linkage и persistence receipts покрыты тестами.
- [ ] Analytics allowlist не содержит фото, текста, имён файлов, EXIF, города/GPS или item payload.
- [ ] Тарифный decision record фиксирует различия 499/999 ₽ и точную quota-семантику.
- [ ] Paywall не блокирует чтение, export/delete и отказ от покупки.
- [ ] Offline/quota/storage failure не создаёт ложное «сохранено» и не теряет исходный гардероб.
- [ ] Mobile 320/360/390/412/430 и desktop проходят keyboard/focus/screen-reader/overflow gate.
- [ ] Детерминизм, latency/memory budget и candidate-pool limits подтверждены на 1, 10, 50 и большом synthetic wardrobe.

## 13. Следующие задачи в порядке выполнения

1. **CAPSULE-02 — decision record тарифов:** владелец продукта фиксирует entitlement 499/999 ₽, 50 + точные 10/15, reset/downgrade/offline.
2. **CAPSULE-03 — domain contract:** `CapsuleV1`, state machine, immutable snapshots, gaps/coverage codes, source guards; без UI и auth-изменений.
3. **CAPSULE-04 — coverage/optimizer spike:** сезон/поездка/офис, laundry/repeat/baggage constraints; deterministic golden cases для 1/10/50 вещей.
4. **CAPSULE-05 — UX prototype:** mobile-first flows всех обязательных веток, включая отказ от покупки и `limited` result; usability test до production-кода.
5. **CAPSULE-06 — persistence/privacy contract:** local repository, read-back receipt, export/delete, analytics allowlist, photo references.
6. **CAPSULE-07 — integration plan:** mapping к wardrobe/candidate/shopping/weather/learning и shared action policy; auth/Supabase остаются отдельной программой.
