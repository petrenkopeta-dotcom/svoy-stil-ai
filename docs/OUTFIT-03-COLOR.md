# OUTFIT-03 — проверяемые правила цвета

Статус: **PASS** для локального детерминированного reasoning по подтверждённым признакам; **HOLD** для распознавания цвета по фото и для утверждений об универсальной «гармонии».  
Версия правил: `color-reasoning/1.0.0`.  
Область: только вещи из личного гардероба пользователя. Покупки, внешние каталоги и retail-рекомендации не входят в контракт.

## 1. Цель и границы

Правила описывают наблюдаемые отношения между цветами вещей в одном кандидате образа: нейтральную основу, повтор семейства цвета, контраст светлоты и нагрузку насыщенностью. Результат — набор воспроизводимых фактов с evidence, а не эстетический приговор, персональный диагноз или процент «насколько образ хорош».

Система не должна:

- выводить цвет из имени вещи, фотографии, категории или иных косвенных признаков;
- утверждать «вам идёт», определять цветотип, тон кожи, тело или демографию;
- называть сочетание объективно гармоничным/негармоничным только по срабатыванию одного правила;
- показывать пользователю числовой color score, скрытый рейтинг человека или ложную точность;
- смешивать demo-вещи и данные личного гардероба в одном расчёте;
- передавать признаки вещей внешнему провайдеру: расчёт выполняется локально и детерминированно.

## 2. Канонический вход

Каждая вещь передаётся как `{ id, confirmed, color }`. В production/personal-контуре участвуют только вещи с `confirmed === true`; фильтрацию выполняет `runStylistReasoningPipeline`. Сам `reasonAboutColors` принимает уже отфильтрованный массив `items`.

| Поле | Допустимое значение | Семантика unknown |
|---|---|---|
| `id` | string или number | без валидного ID цвет вещи не участвует |
| `color.known` | `false` или отсутствует | `false` всегда исключает цвет, даже если рядом записано `family` |
| `color.family` | непустая строка, стабильный taxonomy token | отсутствующее/пустое значение исключает весь цвет; регистр и края нормализуются |
| `color.neutral` | boolean | только явное `true` означает нейтраль; иное значение не считается нейтралью |
| `color.lightness` | число `0..100` | отсутствующее/невалидное значение исключается только из правил светлоты |
| `color.saturation` | число `0..100` | отсутствующее/невалидное значение исключается только из правил насыщенности |
| `color.role` | `base`, `support`, `accent` | отсутствующее/невалидное значение не используется в правилах акцентов |

`unknown` не заменяется `#808080`, `0`, средним значением или догадкой. Placeholder из legacy-адаптера не является подтверждённым цветовым фактом и не должен попадать в personal reasoning без явного подтверждения пользователя.

## 3. Общий выход и проверяемость

Движок возвращает `{ engine_version, facts }`. Каждый факт содержит только:

- `code` — стабильный код правила;
- `evidence` — агрегаты и применённые границы;
- `item_ids` — ID только тех вещей, которые поддерживают факт, в порядке исходного образа;
- `severity` — `info` или `warning`;
- `rule_version` — точная версия правила.

Одинаковый валидный вход обязан давать побайтно эквивалентный структурированный результат. UI получает allowlisted коды через pipeline и отображает отдельно проверенный текст; сырые числовые evidence не превращаются в публичный score.

## 4. Правила палитры

### 4.1 Достаточность и unknown

`COLOR_DATA_INSUFFICIENT` (`warning`) срабатывает, если после нормализации известно меньше двух цветов. Evidence: `known_item_count`, `total_item_count`, `required_known_item_count: 2`. После этого остальные цветовые правила не вычисляются.

Это единственный корректный итог для нулевого/одного известного цвета. Неизвестные вещи не перечисляются в `item_ids`, а их заявленные рядом family/role не протекают в evidence или объяснение.

### 4.2 Нейтрали и один акцент

`NEUTRAL_BASE_SINGLE_ACCENT` (`info`) срабатывает, когда:

- есть хотя бы одна вещь с `neutral === true`;
- ровно одна ненейтральная вещь имеет `role === "accent"`.

Evidence: `neutral_count`, `accent_count: 1`; `item_ids` содержит нейтрали и акцент. Правило фиксирует структуру палитры, но не доказывает, что акцент подходит человеку или случаю.

### 4.3 Повтор цвета и родственные оттенки

`COLOR_FAMILY_REPEATED` (`info`) срабатывает, если один или несколько нормализованных `family` встречаются минимум дважды. Evidence: `repeated_family_count`, `repeated_item_count`; в `item_ids` входят все вещи повторённых семейств.

`RELATED_SHADES_PRESENT` (`info`) срабатывает, если ненейтральных вещей минимум две и у всех одно `family`. Evidence: `chromatic_item_count`, `chromatic_family_count: 1`.

Оба факта могут сработать одновременно: первый подтверждает повтор taxonomy token, второй — единое семейство среди всей хроматической части. Близость разных family, комплементарность и temperature harmony версия `1.0.0` не вычисляет.

### 4.4 Контраст светлоты

Правила применяются, только если валидная `lightness` есть минимум у двух вещей.

`MODERATE_LIGHTNESS_CONTRAST` (`info`) срабатывает при диапазоне `max(lightness) - min(lightness)` от `25` до `65` включительно. Evidence содержит фактический `lightness_range` и границы `25`, `65`.

`LIGHT_DARK_BALANCED` (`info`) срабатывает, когда одновременно:

- есть хотя бы одна светлая вещь: `lightness >= 65`;
- есть хотя бы одна тёмная вещь: `lightness <= 35`;
- разница количества светлых и тёмных вещей не больше `1`.

В `item_ids` второго факта не входят средние по светлоте вещи. «Balanced» означает только баланс количества по этим порогам, не баланс визуальной площади, принта или восприятия.

### 4.5 Нагрузка насыщенностью

Правила применяются, только если валидная `saturation` есть минимум у двух вещей. Насыщенная вещь: `>= 70`; сдержанная: `<= 45`.

`SATURATION_SINGLE_FOCUS` (`info`) срабатывает при ровно одной насыщенной и хотя бы одной сдержанной вещи. Evidence: `vivid_item_count: 1`, `restrained_item_count`.

`SATURATION_LOAD_HIGH` (`warning`) срабатывает, если насыщенных вещей минимум три и их доля среди вещей с измеренной насыщенностью строго больше `0.6`. Evidence: `vivid_item_count`, `measured_item_count`, `vivid_share`, округлённая до двух знаков. Ровно `0.6` не срабатывает.

Правила взаимоисключающие в одном проходе из-за ветки `if/else if`. Warning означает «образ может восприниматься активным», а не ошибку и не запрет.

### 4.6 Несколько акцентов

`MULTIPLE_ACCENTS_CONFLICT` (`warning`) срабатывает, если есть минимум две ненейтральные вещи с `role === "accent"` и они представляют минимум два разных `family`. Evidence: `accent_item_count`, `accent_family_count`.

Код сообщает о конкурирующих акцентных ролях. Он не утверждает, что сами цвета несовместимы: пользователь может сознательно выбрать активную палитру.

## 5. Матрица граничных примеров

| Вход | Ожидаемые факты | Не должно появиться |
|---|---|---|
| 0 известных цветов | `COLOR_DATA_INSUFFICIENT` | любые выводы о палитре |
| 1 известный + `known:false` с заполненным family | `COLOR_DATA_INSUFFICIENT`; только известный ID в evidence | family неизвестной вещи |
| нейтраль + 1 ненейтральный accent | `NEUTRAL_BASE_SINGLE_ACCENT` | утверждение «вам идёт» |
| 2 ненейтральные вещи одного family | `COLOR_FAMILY_REPEATED`, `RELATED_SHADES_PRESENT` | вывод о близости разных family |
| lightness `35` и `65` | `MODERATE_LIGHTNESS_CONTRAST`, `LIGHT_DARK_BALANCED` | исключение пороговых значений |
| диапазон lightness `24` или `66` | нет `MODERATE_LIGHTNESS_CONTRAST` | округление до допустимой границы |
| saturation `[70, 45]` | `SATURATION_SINGLE_FOCUS` | `SATURATION_LOAD_HIGH` |
| saturation `[70, 80, 90, 20, 30]` | доля `0.6`, поэтому нет `SATURATION_LOAD_HIGH` | трактовка `>= 0.6` |
| saturation `[70, 80, 90, 20]` | `SATURATION_LOAD_HIGH`, share `0.75` | публичный процент качества |
| 2 accent одного family | возможен повтор, но нет `MULTIPLE_ACCENTS_CONFLICT` | ложный конфликт ролей |
| 2 accent разных family | `MULTIPLE_ACCENTS_CONFLICT` | запрет сохранить/надеть образ |

## 6. Demo/personal и privacy

- Источник набора маркируется до вызова reasoning как `demo` или `personal`; смешанный набор отклоняется вызывающим слоем.
- Demo fixture не копируется в личный гардероб и не считается пользовательским предпочтением без явного действия пользователя.
- Personal-расчёт использует только принадлежащие текущему локальному профилю подтверждённые карточки. В evidence остаются внутренние item ID и агрегаты, без фото, имени пользователя и свободного текста.
- Факты вычисляются локально; телеметрия, если появится отдельно, должна принимать только allowlisted коды/версии и не включать палитру или item ID по умолчанию.
- Отсутствие данных безопасно: показать «нужно подтвердить цвета хотя бы двух вещей», а не достраивать ответ.

## 7. Acceptance gate

**PASS**, если одновременно выполнено:

1. Вход содержит только подтверждённые personal-вещи одного владельца либо изолированный demo-набор.
2. Все девять кодов и пороги совпадают с `src/colorReasoning.js` версии `color-reasoning/1.0.0`.
3. Для каждого факта воспроизводимы `rule_version`, `item_ids` и структурированное evidence.
4. Unknown не влияет на family/роль/метрики и не раскрывается в объяснении.
5. Публичный UI показывает качественные формулировки без score и допускает пользовательский выбор вопреки warning.
6. Автотесты покрывают детерминизм, обе границы lightness, saturation `0.6`/`>0.6`, `known:false`, malformed input и конфликт акцентов.

**HOLD**, если цвет получен неподтверждённым распознаванием, смешаны demo/personal данные, отсутствует версия правила/evidence, unknown заменён догадкой или UI выдаёт факт за персональную/универсальную оценку гармонии.

## 8. Evidence и зависимости

Кодовая основа:

- `src/colorReasoning.js` — нормализация, пороги, коды, evidence и версия;
- `src/colorReasoning.test.js` и `src/colorReasoning.fixtures.js` — детерминизм, базовые позитивные и unknown-safe сценарии;
- `src/stylistReasoningPipeline.js` — допуск только `confirmed === true`, allowlist публичных кодов;
- `src/stylistExplanation.js` — качественные тексты и практические советы без числового score;
- `docs/color-reasoning.md` — текущий статус production recognition **NO-GO**;
- `docs/domain-model.md` — разделение AI suggestion и user-confirmed values, владение `ClothingItem`;
- `docs/stylist-candidate-engine-v1.md` — запрет публичного числового score.

Зависимости следующего шага:

- вызывающий слой должен гарантировать owner boundary и изоляцию `demo | personal` до reasoning;
- UI обязан различать `info`, `warning` и `COLOR_DATA_INSUFFICIENT`, не блокируя пользовательское решение;
- для полного acceptance нужны отдельные boundary-тесты на lightness `24/25/65/66` и saturation share `0.6`/`>0.6`; текущие тесты подтверждают основную реализацию, но не все перечисленные границы;
- любое изменение taxonomy, порога или смысла кода требует новой `rule_version` и обновления этого документа/тестов.
