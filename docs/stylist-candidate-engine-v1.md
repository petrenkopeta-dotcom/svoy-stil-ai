# Stylist Candidate Engine v1

Статус: реализован изолированно; интеграция с контрактами этапа 1 — **PASS**.

`src/stylistCandidateEngine.js` детерминированно собирает технически полные комплекты (`top + bottom + shoes` либо `dress/one_piece + shoes`), опционально добавляет верхнюю одежду и аксессуар, сохраняет `anchorId` и применяет hard constraints до ранжирования.

Ранжирование использует шесть объяснимых компонентов: `color`, `silhouette`, `occasion`, `weather`, `personal`, `comfort`. Весовые профили неизменяемы и версионированы: `balanced-v1`, `comfort-first-v1`, `occasion-first-v1`. Стабильность обеспечивается сортировкой входных групп по ID и подписью комплекта как tie-breaker. Diversity применяется после основного ранжирования через детерминированный штраф за повторное использование вещей. Внутренний candidate pool ограничен 5000 комбинациями (настраивается в безопасном диапазоне 100–10000), чтобы ограничить latency и память на больших гардеробах.

Публичный кандидат не содержит числового score. Он содержит `rankingLevel`, категориальный `scoreBreakdown` (`strong | compatible | tradeoff`), краткое объяснение, версии генератора и весов. Причины отсутствия кандидатов возвращаются как стабильные коды.

## Границы и адаптер

Канонический вход принимает `GarmentStyleFeatures` и `StylistRequest` из `stylistReasoningSchemas.js`, а каждый результат включает валидный `CandidateOutfit`. `adaptCandidateItem` также поддерживает подтверждённые поля `ClothingItem` из `docs/domain-model.md` и demo-поля `type`, `name`, `color`, `style`, не изменяя существующие контракты или UI. Production recognition, внешние/provider/OpenAI-вызовы и любые выводы о цветотипе, теле или демографии отсутствуют.

Для следующего этапа остаётся решить, где хранится внутренний числовой ranking trace. В пользовательский результат он намеренно не входит. `src/main.jsx` не изменён; подключение UI и anchor-flow остаётся отдельной задачей.
